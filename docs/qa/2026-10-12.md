# October browser/server maintenance

This maintenance continues the prior acquisition and browser regression work. Only VeyraBrowser and VeyraServer are in scope; VeyraOS and both backup repositories are unchanged. The detailed 16-site results and selected images are stored in VeyraBrowser at `docs/qa/2026-10-12/`.

## Server changes

- **JavaScript rewriting:** remove the expression-breaking service-worker substitution. Use `es-module-lexer/js` for static/literal dynamic imports, preserve bare aliases, and keep module identity stable across importing parents, script tags and modulepreload.
- **Casting routes:** create returns `browserToken`; HTTP device join returns `deviceToken`. Receiver poll/send/close requires the browser capability; device poll/push requires its distinct device capability.
- **WebSocket resume:** an existing receiver session requires `token` in the `/ws/cast?role=browser&session=…` handshake. Device pairing still uses the short pairing code; deployment rate/origin hardening remains a follow-up.
- **Transport correctness:** HTTP and WebSocket receivers/senders share a relay, including pairing, commands, frames and disconnects. Replaced connections cannot close the replacement, and all associated maps/queues are cleaned.
- **Bounds:** cryptographic pairing-code generation, uniqueness checks, default 64 simultaneous cast sessions, 400 KB image frame limit, 512 KB WS payload limit, latest-frame polling queue and backpressure-aware WS frame delivery.
- **Privacy:** public `/api/cast/sessions` returns aggregate statistics rather than IDs/codes. `/api/cast/push/:sessionId` returns 410; use authenticated `/api/cast/device/push/:deviceId`. The unused third-party QR-image URL is no longer advertised.

## Deployment compatibility

Coordinate release with the browser `8.28.28-browser-qa` changes. An old client lacks cast capabilities and will receive 403 from protected routes; do not silently make the new endpoints accept missing tokens to retain backward compatibility.

A controlled maintenance window or staged paired release is preferable to leaving one half updated. Existing cast sessions are process-local and are ended by a server restart; users must generate fresh codes. These review-branch changes have not been deployed to Render or the public Pages site.

## Verification

The complete `npm test` suite passes locally and now includes the new tests by default. Casting adds 53 transport/lifecycle/capacity checks and 20 real HTTP authorization/routing/isolation checks; rewriting adds seven expression samples and nine module checks. Production dependency audit reported no known vulnerabilities at test time.

The browser's actual receiver paired to a simulated device, ingested authenticated image frames and exercised Start/Stop/Disconnect. This does not establish physical-device capture, iOS/Android permission support, Chromecast/AirPlay or multi-stream same-window UI support.

## Open items

TikTok and Internet Archive still rendered blank in the patch-local follow-up; eliminating captured exceptions did not establish end-to-end success. Public GitHub rendered in the local follow-up, but that comparison used different hosting conditions and is not a speed benchmark.

Normal-browser Google OAuth for Veyra identity remains unimplemented pending registered client/callback configuration. Google prohibits developer-controlled embedded authorization and requires compliant HTTPS redirects and secure token handling in its [OAuth policies](https://developers.google.com/identity/protocols/oauth2/policies). Signing into Google in Chrome is not evidence that a separate Veyra proxy session has acquired its cookies.

Review deployment-specific pairing rate limits, origin checks, device/account binding, memory/CPU limits and Chromium opt-in before exposing new functionality more broadly. Do not increase browser-engine capacity or claim universal Fast Proxy compatibility on the basis of this smoke pass.
